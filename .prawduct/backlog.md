- **Arrangement-clip move warning lacks `clip_id` breadcrumb.** `_apply_arrangement_clips_for_track` (`pull.py:~1381`) emits two parallel signals when a placement is moved in Live: a `remove_arrangement` event for the old position and an Ableton-only warning for the new one. The user-visible warning currently only carries the new `(start_bar, end_bar)` — no reference to the removed row's `clip_id` or display name, so a user re-adding via DB mutators has no breadcrumb back to which clip the placement belonged to. Two options: (a) emit a combined "likely-move" warning when a remove and an Ableton-only placement co-occur on the same track within the same diff, or (b) include the removed `clip_id` + `clip_name` in the remove detail so the warning chain reads naturally. Non-blocking; backlog-class refinement that improves UX for the move case. (critic, M+1 final 2026-05-17)
- **`_apply_arrangement_clips_for_track` re-fetches full song arrangement per linked track.** `pull.py:~1349` calls `Q.get_arrangement_for_song(conn, song_id)` and Python-filters by `track_id` — runs once per linked authoring track. A `get_arrangement_for_track(conn, track_id)` query would be cleaner and scales better with track count. Not a correctness issue at single-song scale today (falling-walking has handful of tracks); files as a minor optimization for future tightening. (critic, M+1 final 2026-05-17)

- **Arrangement-clip pull: duplicate `(start_bar, end_bar)` keys collapse silently.** `_apply_arrangement_clips_for_track` (`pull.py`) keys both the DB-side and Ableton-side placements by `(start_bar, end_bar)` rounded to 1/1000 of a bar. If two placements on the same track land at identical positions (rare in practice — Live allows overlap but exact-coincidence is a user authoring oddity), the dict-build silently keeps the last one and the diff under-reports. Decide between (a) using a multi-set match (list-per-key with FIFO drain), (b) adding a uniqueness assertion that warns when collisions are seen, or (c) accepting the limitation explicitly in the docstring. Non-blocking — no real song has overlapping arrangement-clip starts today. (critic, M+1-3b 2026-05-17)

- **Install-skill polish — four low-probability footguns.** Flagged by both Critic round 2 and PR reviewer on `fix/install-skills-cross-platform`; none gate the PR but worth a future pass. (b) `existing_mcp_config_files` looks up `projects[str(cwd)]` with exact string equality, so a symlinked cwd or a Windows case-difference between the OS and what `claude mcp add` recorded misses the entry — normalize via `Path.resolve()` on both sides. - **Hallucinote-side quantize / swing / groove module.** During Wave M-3, the user reaffirmed the DB-as-source-of-truth principle for note timing: quantize, swing, and groove templates are pure-math transforms that should live in Hallucinote (Python/SQL), not call Live's `clip.quantize()` or use Live's Groove Pool. The MCP surface therefore exposes NO `quantize` / `apply_groove` / `extract_groove` actions; Hallucinote computes the result and pushes pre-grooved notes via `ableton_clip(action='replace_notes', ...)`. Scope: (a) `src/hallucinote/timing/quantize.py` — pure functions taking `(notes, grid, amount, swing) → notes`; (b) `grooves` table for storable timing templates portable across songs; (c) `apply_groove(notes, groove_template) → notes` and `extract_groove(notes) → groove_template`; (d) generator-layer wiring so `generate_*` outputs can optionally pass through quantize/groove before persistence. Sized as a single chunk after Wave M completes (or sooner if a song needs it). Test discipline: example-based fixtures for known input→output; consider Hypothesis property tests for the round-trip invariant (extract-then-apply approximately recovers the template). (reflection, Wave M-3 user pivot 2026-05-17)

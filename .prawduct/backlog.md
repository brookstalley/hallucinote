- **Hallucinote-side quantize / swing / groove module.** During Wave M-3, the user reaffirmed the DB-as-source-of-truth principle for note timing: quantize, swing, and groove templates are pure-math transforms that should live in Hallucinote (Python/SQL), not call Live's `clip.quantize()` or use Live's Groove Pool. The MCP surface therefore exposes NO `quantize` / `apply_groove` / `extract_groove` actions; Hallucinote computes the result and pushes pre-grooved notes via `ableton_clip(action='replace_notes', ...)`. Scope: (a) `src/hallucinote/timing/quantize.py` — pure functions taking `(notes, grid, amount, swing) → notes`; (b) `grooves` table for storable timing templates portable across songs; (c) `apply_groove(notes, groove_template) → notes` and `extract_groove(notes) → groove_template`; (d) generator-layer wiring so `generate_*` outputs can optionally pass through quantize/groove before persistence. Sized as a single chunk after Wave M completes (or sooner if a song needs it). Test discipline: example-based fixtures for known input→output; consider Hypothesis property tests for the round-trip invariant (extract-then-apply approximately recovers the template). (reflection, Wave M-3 user pivot 2026-05-17)
- **Retarget `replace_session_clip` to atomic `ableton_clip(action='create', replace=True, notes=...)`.** Wave M-3 left the planner emitting the Hallucinote-canonical `replace_session_clip` for unlinked clips (3-step agent emulation: delete + create + replace_notes). The new MCP surface already supports the atomic single-call path via `ableton_clip(action='create', replace=True, notes=...)` — schema-stable, just needs the planner switch + an `_apply_clip_create` to record the new `clip_index` link binding. Sized as a small chunk that drops one more `_emulate_*` alias and saves two round-trips per clip iteration. (reflection, Wave M-3)
- **Return-track mute/solo round-trip.** The `returns` table currently has columns for `name`, `position`, `volume`, `pan`, `color` — but NOT `mute` or `solo`. The MCP-side `ableton_return(action='info')` handler returns `mute` / `solo` fields, and `_apply_return_info` would diff them if the DB supported it. Until the schema grows, Ableton-side return mute/solo edits never reach the DB. Fix: add `mute` / `solo` INTEGER columns to `returns` (matching tracks), update `_RETURN_FIELDS` + `update_return`, enable the dead `return_mute` / `return_solo` ack-only keys in `push._ACK_ONLY_KINDS`, and re-enable mute/solo in `_apply_return_info`. Migration concern: existing songs will need DEFAULT 0 backfill. Non-blocking — single-user authoring rarely needs return mute/solo. (reviewer, Wave M-2)
